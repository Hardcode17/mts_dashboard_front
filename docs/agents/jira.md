# Jira для агентов

Правила работы с задачами для AI-агентов команды MTS Dashboard.

> Каноническая версия этого файла живёт в `mts_dashboard_data/docs/agents/jira.md`.
> Копии лежат в `mts_dashboard_front` и `mts_dashboard_backend`.
> При изменении обнови все три копии.

## Контекст

- Сайт: `sokolenkonikita12ru.atlassian.net`
- Проект: `KAN` — HARDCODE MTS HACK
- Доска: **KAN board** (одна на frontend, backend и data)
- Репозиторий задачи определяется меткой:
  - `repo:frontend`
  - `repo:backend`
  - `repo:data`
- Типы задач: `Задача`, `История`, `Эпик`, `Subtask`.
- Метка `agent` означает, что задачу можно брать агенту.
- Метка `blocked` означает, что агент уперся и нужен человек.

## Статусы и переходы

| Статус | ID | Переход | ID перехода |
|---|---|---|---|
| К выполнению | `10003` | `К выполнению` | `11` |
| В работе | `3` | `В работе` | `21` |
| В процессе проверки | `10004` | `In Review` | `31` |
| Готово | `10005` | `Готово` | `41` |

Название перехода и название статуса могут не совпадать: у перехода в «В процессе проверки» имя `In Review`. Поэтому всегда сверяйся с `to.name` из `listJiraIssueTransitions`, а не угадывай по имени перехода. ID выше актуальны для проекта `KAN`, но если переход не найден — запроси список заново.

## Подключение MCP

В репозитории должен быть `opencode.jsonc`:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "atlassian": {
        "type": "remote",
        "url": "https://mcp.atlassian.com/v2/mcp"
      }
    }
  }
}
```

Авторизация — под своим аккаунтом Jira:

```sh
opencode mcp auth atlassian
# или в сессии: /mcps → atlassian → sign in
```

Не коммить токены и не используй общий аккаунт. Все действия должны быть от твоего пользователя, чтобы в истории Jira было видно, чей агент что сделал.

Основные инструменты:

- `searchJiraIssuesUsingJql` — поиск задач.
- `getJiraIssue` — чтение задачи и чеклиста.
- `createJiraIssue` — создание задачи.
- `editJiraIssue` — изменение полей и описания.
- `transitionJiraIssue` — смена статуса.
- `addOrEditJiraIssueComment` — комментарии.
- `listJiraIssueTransitions` — доступные переходы.

## Как брать задачу

1. Ищи только по своему репозиторию:

   ```sql
   project = KAN
     AND labels = "agent"
     AND labels = "repo:frontend"
     AND statusCategory != Done
     AND assignee IS EMPTY
   ORDER BY created ASC
   ```

   Замени `repo:frontend` на `repo:backend` или `repo:data`. Лимит — 10 результатов.

2. Перед созданием новой задачи проверь, нет ли похожей:

   ```sql
   project = KAN AND summary ~ "ключевые слова" ORDER BY created DESC
   ```

3. Не бери задачи:
   - с чужой меткой `repo:*`;
   - уже назначенные на другого человека;
   - со статусом «Готово»;
   - с меткой `blocked`, пока человек не снимет её.

4. Взял задачу:
   - назначь на владельца агента через `editJiraIssue` (`assignee` принимает email или display name);
   - переведи в **В работе**;
   - добавь комментарий `agent: claimed`.

   Если создаёшь новую задачу через `createJiraIssue`, `assignee` требует `accountId`. Если его нет — создай без исполнителя и назначь отдельным `editJiraIssue`.

## Ветки, коммиты, PR

- Ветка: `feature/KAN-123-короткое-имя`, для бага — `fix/KAN-123-короткое-имя`.
- Коммит: Conventional Commits с ключом задачи, например:

  ```text
  feat(ui): add dashboard filters (KAN-123)
  fix(api): handle empty response (KAN-124)
  ```

- В заголовке PR обязательно указывай `KAN-123`.
- После открытия PR добавь ссылку на него комментарием в задаче и переведи задачу в **В процессе проверки**.
- В **Готово** переводи только после мержа PR или явного подтверждения человека. Не закрывай задачи самостоятельно.

## Чеклисты

Если в описании задачи есть чеклист:

1. Прочитай описание как markdown: `getJiraIssue` с `responseContentFormat: "markdown"`.
2. Найди **только свою** строку.
3. Замени `- [ ]` на `- [x]` только в ней. Не меняй чужие пункты, не переставляй и не удаляй их.
4. Сохрани описание через `editJiraIssue` с `contentFormat: "markdown"`.
5. Добавь комментарий, что пункт отмечен.

Перед сохранением перечитай описание ещё раз: четыре агента могут редактировать один чеклист одновременно. Если твоя правка затёрла чужую галочку — верни её и сохрани снова.

## Ограничения

- Не создавай дубли: сначала поиск, потом создание.
- Не удаляй задачи и комментарии.
- Не делай bulk-изменения и не меняй спринты без человека.
- Не назначай задачи на других людей.
- Не трогай задачи других репозиториев.
- Не пиши в Jira секреты, токены, персональные данные и внутренние URL.
- Не ставь статус «Готово», если PR не смержен и человек не подтвердил.
- Уперся — поставь метку `blocked`, объясни причину в комментарии и остановись. Не переключайся молча на другую задачу.

## Связи между репозиториями

- Агент работает только в своём репозитории. Задачи других репозиториев берут их агенты.
- Если задача зависит от другой, свяжи их в Jira через `blocks` / `is blocked by` и укажи ключ в комментарии.
- Для сквозной фичи создавай отдельные задачи в frontend, backend и data с одной меткой `epic:KAN-<номер>` или общим эпиком.
