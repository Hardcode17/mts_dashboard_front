# Изменение назначения из рабочего места

В карточке INC откройте «Изменить в ITSM». Выберите исполнителя из справочника внешнего сервиса, укажите команду и при необходимости статус. При завершении укажите решение. После «Сохранить в ITSM» форма показывает подтверждённые сервисом команду, исполнителя и статус; реестр и история обновляются в сессиях смены. Для передачи принятой персональной задачи доступна кнопка «Передать исполнителю» в разделе «Моя смена». Она отправляет изменение группы тем же путём.

Подключение выбирается на стороне сервера при запуске:

- `MCC_DASHBOARD_URL` — адрес Spring API с KAN-58. Адаптер использует `GET /api/dashboard/users` и `GET/PATCH /api/dashboard/incidents/{INC}`. Для защищённого Spring API на входе нужен пользовательский заголовок Bearer из авторизованной сессии или прокси. При отсутствии допуска форма показывает ответ об ошибке доступа.
- `MCC_ITSM_URL` — отдельный ITSM-мок команды на изолированном стенде. Сервер читает `GET /user` и `GET /itsm_incident/{sysId}`, отправляет `PATCH /itsm_incident/{sysId}`. Сырые карточки двух сервисов должны иметь одинаковые `id` и `sysId`. Если старый снимок не содержит `sysId`, адаптер запрашивает запись по номеру INC и использует полученный `sysId` для PATCH. Это поддерживает командный ITSM-мок KAN-57.
- Когда заданы оба адреса, используется Spring API. Без подключения отображается редактор с подписью «Мок официального источника»; изменения такого режима остаются в SQLite.
- Для запуска Vite или `npm start` адрес должен быть доступен процессу Node.js. Для Compose адрес должен быть доступен из сети контейнера. Реальные параметры подключения передаёт оператор; продуктивный доступ требует аутентифицированного бэкенда.

Внешний редактор отправляет только изменённые поля. При подтверждении рабочая копия принимает состояние ITSM. Ошибка чтения/записи не заменяется локальным успехом. При тайм-ауте результат записи может быть неизвестен; «Перечитать карточку» делает новый GET. Внешняя ITSM получает группу, исполнителя, статус и текст решения согласно контракту. Приоритет и срок отображаются в обзоре INC. Повторное изменение исходного снимка применяет его данные по действующим правилам импорта. При поступлении снимка во время PATCH подтверждённое изменение объединяется с независимыми правками. Если сменился sysId или то же поле получило третье значение, форма показывает конфликт и предлагает перечитать источник.

## Отдельный источник для демонстрации

Командный сервис находится в `mts_dashboard_backend/itsm-mock` ветки `feature/podkopaev-kan-backend` (проверена `28ba2e1`). В checkout этой ветки с JDK 21 соберите `sh gradlew :itsm-mock:bootJar`. Для отдельного процесса задайте `SERVER_ADDRESS=127.0.0.1`, `SERVER_PORT=5392`, `ITSM_MOCK_FIXTURE_FILE` с полным путём к начальному JSON и `ITSM_MOCK_STATE_FILE` в отдельном каталоге. Отключите плановую доставку через `ITSM_MOCK_SCHEDULED=false`; сервис при старте также требует `ITSM_MOCK_TOKEN_URL`, `ITSM_MOCK_CLIENT_ID` и `ITSM_MOCK_CLIENT_SECRET`. На изолированном стенде с выключенной доставкой подходят петлевой URL и тестовые значения. Запустите `java -jar itsm-mock/build/libs/itsm-mock.jar`. Для чистого теста используйте новый каталог состояния.

Укажите пульту `MCC_ITSM_URL=http://127.0.0.1:5392` и `MCC_SOURCE_FILE` с тем же исходным JSON. После изменения выполните отдельный GET на `/itsm_incident/{sysId}` официального приложения и сверьте `assignedEmployeeLogin`, `assignedGroupName`, `stateEnum`. Проверка по сетевому ответу ITSM подтверждает внешнюю запись независимо от содержимого экрана.
